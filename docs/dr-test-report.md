## Purpose

Measure, with a repeatable script, how long the demo takes to serve again from the second region in each direction (RTO), whether any acknowledged write is lost (RPO of the planned switchover) and where the time goes. The 15-minute RTO target of the project is a target, not a result of this report.

## Method

A runner on a workstation drives the real prod environment through the public API and the GitHub workflows. Phases, in order: `baseline` (steady load on the primary region), `fence` (the `simulate-outage` workflow throttles the functions of the primary region to zero), `to-secondary` (the `failover` workflow promotes the secondary region), `steady-secondary`, `to-primary` (the `failover` workflow fails back), `steady-primary` and `consistency` (final ledger check). Four probes run for the whole drill: a write probe (one attempt every 1 s, deposits and withdrawals of 0.01 alternating, so the ledger stays net zero; an unacknowledged movement is retried with the same idempotency key), a read probe (`GET /account` every 5 s), a health probe (`GET /health?deep=true` every 5 s) and a sign-in probe against the secondary region (every 10 s). A DNS watcher polls the API name every 2 s from the workstation. Replication lag is read from CloudWatch after the drill, once the runner has waited 120 s for the last datapoints. Times are UTC. Percentiles are nearest-rank. The drill dispatches the workflows by script; the switch itself is the manual weighted-routing change of the project, run by the workflow.

## Environment

- Regions: primary `us-east-2` (writer at the start), secondary `us-west-2`.
- Database: Aurora PostgreSQL Global Database, instance class `db.r6g.large`, engine version `16.15` (read from `docs/technical.md`).
- Traffic: Route 53 weighted records switched by the `failover` workflow; the probes call the public API name, so they cross the same path as a user.
- No account data is included in this report.

## Limitations

- One run from one workstation and one network path: the numbers are a sample, not a distribution.
- DNS is observed from the workstation through one resolver, every 2 s. Other resolvers, browsers and caches are not measured.
- Only the planned path is exercised (switchover with the primary region simulated as unavailable by throttling its functions). An unplanned failover, with its own RPO, is not measured; the replication lag is only a bound.
- The switch is a manual workflow dispatched by the runner. Detection time and the time a person takes to decide are not measured; the decision time in the tables is the runner's.
- The load is synthetic and net zero: about one write every 1 s, far below production traffic.
- Resolution is bounded by the probes: writes about 1 s, reads and health 5 s, sign-in 10 s, DNS 2 s, GitHub timestamps 1 s, replication lag one datapoint per 60 s.
- Replication lag is read after a 120 s wait for CloudWatch; the last 1 to 3 minutes of lag can still be missing.
- Workflow times come from GitHub and the probe times from the workstation clock; their skew is not corrected.
- The RPO is checked against the ledger of the probe movements; movements that were not acknowledged may or may not have committed (uncertainty band).
